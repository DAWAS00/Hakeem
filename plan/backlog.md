- **Run the pgTAP RLS test against a real instance.** `supabase/tests/profiles_rls_test.sql` was written but never executed — no Supabase CLI available in the build environment. Must run `supabase test db` before trusting the `profiles` RLS policies in production.
- **Live end-to-end login untested.** All auth-slice tests use fakes/stubs. Needs an actual Supabase project (or `supabase start` locally) plus `env.json` (copy `env.example.json`) to confirm phone and national-ID login actually work end-to-end, including the `resolve-login-identifier` Edge Function round-trip.
- **`resolve-login-identifier` has no audit log.** It resolves national IDs to emails but doesn't record who queried what, when — for a gov healthcare app, failed/successful identifier-resolution attempts should probably be auditable beyond just the rate-limit counter.
- **Migrate signup off Dio/`api.hakeem.jo`.** Deliberately out of scope for the login slice — the signup flow (multi-step form: personal/contact/health/consent) is materially bigger and needs its own `plan/signup_slice_technical_plan.md` following the auth slice's template before starting.
- **`UserModel.fromJson` is a temporary dual-path.** Kept only because `signup_remote_datasource.dart` still targets the legacy REST API. Delete it once signup migrates.
- **Data residency / Sanad OIDC open questions from `plan/architecture_redesign_plan.md` are still unanswered** — they block deciding whether self-hosted Supabase is required and how Sanad SSO actually integrates. Needed before `family_hub` (the next slice) can finalize its own auth-adjacent RLS design.

## From: /plan-eng-review of the login slice (2026-07-05)

- **No E2E/widget coverage for the login screen submit flow or `loginWithBiometric()`.** Only a smoke test exists today (`widget_test.dart`: "renders without crashing"). The actual submit → loading → success/error-banner cycle, and the biometric fallback path, are unverified end-to-end.
- **`login_identifier_attempts` rate limiting is IP-only and bypassable.** In a NAT-heavy mobile market, many real users share IPs (false-positive risk) and an attacker behind a VPN/proxy rotation can bypass it entirely (enumeration risk against national IDs, sensitive PII for a gov healthcare app). Consider a secondary per-national-ID limit, CAPTCHA, or device fingerprinting — needs its own design discussion, not a quick patch.
- **Consider a synthetic-email redesign for national-ID login** (e.g. store `{national_id}@nid.internal` as the Supabase Auth email at signup) that would let the client call `signInWithPassword` directly, eliminating the `resolve-login-identifier` Edge Function, its SECURITY DEFINER RPC, and the rate-limit table entirely. Real architectural simplification, but a redesign of already-shipped code and the template every future feature copies — worth a dedicated look before more features copy the current Edge Function pattern.
- **PII-in-logs pre-production gate.** `RepositoryGuard` passes raw exception objects (potentially containing attempted identifiers) to `Talker.handle()` as `debugDetails`. Currently low-risk — `main.dart` configures Talker console-only, no file/remote sink. **Before adding any persistent or remote Talker sink (crash reporting, log shipping), add redaction for identifying fields in `debugDetails` first** — don't ship PII into a log aggregator by default.

## From: Supabase migration foundation hardening + signup slice (docs/features/auth.md, 2026-07-05)

- **New signup users cannot log in through the existing login screen.** Signup uses phone-OTP verification only (`signInWithOtp`/`verifyOTP`) and never sets a password, but `LoginNotifier.login`'s phone path calls `signInWithPassword`. This was a deliberate, user-approved decision to ship signup now and add OTP-based login as a fast-follow — but it must land before signup is usable end-to-end, not treated as optional polish.
- **`signup_screen.dart`'s OTP step (`Step5Otp`) has no resend cooldown/rate-limit UI.** `sendOtp()` can be called repeatedly via the "resend" button with no client-side throttling — relies entirely on Supabase's own SMS rate limits. Fine for now, but worth a cooldown timer before this ships to real users (cheaper than hitting Supabase's rate limit and showing a raw error).
- **Email linking in `SignupRemoteDatasourceImpl.verifyOtp` is best-effort but not optional-feeling.** If a user provides an email during signup and `updateUser(email:)` fails, the whole `verifyOtp` call fails (propagates as a `Failure`) even though the phone verification itself succeeded — meaning a transient email-update error blocks account creation entirely. Consider decoupling: let phone verification always succeed, retry/prompt for email linking separately if it fails.
- **`dio`/`dio_provider.dart`/`flutter_secure_storage` were removed from the project** (both auth paths were the last consumers). If a future feature genuinely needs a non-Supabase HTTP client or secure token storage, re-add deliberately rather than assuming it's still there.
- **`RepositoryGuard` and `json_field_x.dart` are now the established shared patterns** (`lib/core/data/`) for any new feature's repository/JSON parsing — `family_hub` (next in the migration queue per `plan/architecture_redesign_plan.md` §5F) should use both from the start rather than hand-rolling try/catch or raw `as` casts, per `supabase/CONVENTIONS.md`.
- **CI (`​.github/workflows/ci.yml`) only runs `flutter analyze`/`format`/`test`.** It does not run `supabase test db` (pgTAP) or any Edge Function integration test — those still require manual execution against a local/real Supabase stack (see Verification Gap in `docs/features/auth.md`).
